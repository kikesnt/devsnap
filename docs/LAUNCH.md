# Launch plan

The goal of the launch is not a spike of traffic that disappears. It is three
things at once:

1. **Impressions** — enough search impressions for the domain to pass an AdSense
   review.
2. **Links** — referring domains, which is what actually moves organic
   rankings for a new domain.
3. **A working tool under load** — because the documented failure mode of a
   viral launch is a crash, and 500 comments saying "it's broken" damage
   perception permanently.

---

## 1. The hook: Code Snapshot

The viral engine is [`/tools/snapshot/`](../src/components/tools/Snapshot.astro).
It turns a code snippet, diff, JSON payload or terminal session into a
shareable PNG, rendered on a canvas in the browser.

**Why this one.** Every other tool on the site solves a problem and disappears.
This one produces an artefact that people post, so distribution is a by-product
of usage. Each post is an advert for the site.

**Why it is defensible.** The incumbents (carbon.now.sh and its clones) render
on a server, which means your code is uploaded to a stranger. This one does not
upload anything, which is both a privacy claim that ranks and a real technical
property.

**The mechanics that matter:**

- Seven themes, a custom accent colour, adjustable font size, optional window
  chrome and a title bar for a filename.
- Exported at 2× resolution, so it does not look soft on a retina display.
- Language detection, so a diff gets green and red lines and a JSON payload
  gets coloured keys.
- Native share sheet where the browser supports it, with a post-to-X intent as
  the fallback.

**Things to check before you post:**

- The output is legible at the size people actually post at. Render a 40-line
  diff and look at it on a phone.
- The share button works on iOS, where the native sheet and clipboard behave
  differently from desktop.
- It survives 200 concurrent requests. It is client-side, so this is mostly a
  question of whether the CDN handles the burst, but test it.

## 3. The launch week

### The order that works

Product Hunt and Reddit behave differently, and the sequence matters.

**Day 1 — Product Hunt.** Launch the Code Snapshot tool, not the site. PH
curates on four filters now: *useful, novel, high-craft, creative*. A tool
that is merely functional does not make the homepage. The differentiators to
show off are the seven themes, the 2× export and the fact that nothing is
uploaded.

- Tag it under *Developer Tools* and *Productivity*.
- Post the launch video on X at the same time. In the 2025 launches that broke
  through, a 120-second video on X drove 38% of the upvotes.
- Answer every comment. A maker who replies to each comment within minutes
  is a documented pattern in the top launches.
- Post a "day 1 update" comment with real usage numbers after 24 hours.

**Day 1 — Hacker News.** Show the work. A post titled "I built a tool that turns
a diff into a shareable image without uploading your code" with a short
technical explanation does better than a launch announcement. HN rewards the
artefact and punishes the marketing framing.

**Day 2 — Reddit.** This is where the long-tail traffic comes from, and where
the mistakes are documented:

- Title describes the **problem**, not the product. "Check out my new Chrome
  extension" underperforms "I built a tool that turns error messages into
  shareable images".
- 150–300 words, one plain paragraph explaining what it does, then why you
  built it, then how to use it in 1-2-3.
- **Link in the first two or three paragraphs, not at the end.**
- Say explicitly that it is free and needs no signup. Requiring an email is
  the single most common reason a free-tool post underperforms, because it
  reads as a lead-generation campaign.
- **State what it does not do.** Pre-empting the negative comments is what
  keeps a thread positive.
- Ask for feedback on one specific thing, not "what do you think".
- If you plan to monetise later, say so now. "Free now, paid features coming"
  is trusted more than a surprise pricing page.

Community fit matters: r/SideProject for something useful and functional,
r/InternetIsBeautiful for something absurd. Posting to the wrong one kills the
thread.

**Day 3–5 — X/Twitter and LinkedIn.** The audience for the snapshot tool is
people who post code. Show the output, not the interface. A 15-second clip of
pasting a diff and getting an image is the whole pitch.

**Day 5 — Dev.to and a technical blog post.** Write about the decision to run
everything client-side, with the reasoning and the trade-offs. This is the
format that gets shared by senior engineers, and it links back to the site with
a real editorial reason.

### Cross-post the guides, not the tools

The guides are the link-earning asset. A guide that answers a question someone
was going to search for gets links from documentation pages, forum answers and
internal wikis, long after launch day. Each guide links to three or four tools,
which is how a reader ends up on a tool page.

- [ ] "How to read a JSON Web Token" → link from any security wiki that
      references JWTs
- [ ] "Cron expressions, and the two rules that catch everybody" → link from
      any ops documentation
- [ ] "UTC vs Local Time" → link from any blog post about timezone bugs
- [ ] "A naming convention for UTM parameters" → link from any marketing ops
      resource

## 4. The first 90 days

### Weeks 1–4: prove the tools work

Watch Search Console for impressions on the tool pages. The tools that rank are
not the ones you expect — a utility with an obvious search intent ("format json
online", "unix timestamp converter") tends to beat a clever one.

For each tool that gets impressions:

- [ ] Is the tool actually satisfying the query? Read the search terms.
- [ ] Does the page have enough content to hold the ranking?
- [ ] Are the internal links pointing at it from the right places?

### Weeks 2–6: apply to AdSense

Once Search Console shows real impressions, apply. See
[`ADSENSE.md`](ADSENSE.md) for the full checklist. Expect the first
application to be rejected, and read the rejection label as a direction:
"low value content" means *demonstrate value, add trust signals, make the pages
more distinct* — not "add more words".

### Weeks 4–12: add tools, not pages

A new tool is a new impression surface and a new internal-link target. A new
programmatic page is a scaled-content risk.

Priority order for the next tools, based on the demand read and the competition
read:

1. **A JSON→CSV/CSV→JSON pair with a spreadsheet paste mode.** Business
   exports are high intent and the spreadsheet angle is under-served.
2. **A `.http` file parser.** Request and response files are the same shape of
   problem as the `.env` parser and the audience is the same.
3. **A JWT generator.** Signed with a local key, for developers who need a test
   token. Same audience, complementary.
4. **A colour palette extractor from an image.** Runs client-side on a canvas,
   and the output is a set of hex values that people paste somewhere.
5. **A cron-to-human-readable converter for the *other* schedulers.** Quartz
   and AWS expressions are increasingly common and the current tool only
   explains Unix cron well.

**What not to build**, based on the 2025–2026 evidence:

- **AI prompt tools.** Saturated with AI-generated listicles and they are the
  canonical casualty of the scaled content abuse updates. Low RPM, high risk.
- **Unit converters.** The SERP is a clone farm, the queries carry no
  commercial intent, and it is a spam-update magnet.
- **Browser games.** The worst RPM niche in every table (0.6×, $4–10) and the
  highest policy risk, because ads on a game screen are an "out of context" risk.
- **Astrology and fortune telling.** Pure template farms, and gambling-adjacent
  inventory restrictions remove the highest-paying demand.
- **"X alternatives" clone directories.** Thin affiliation is the codified
  policy against exactly this shape.
- **Fake receipt generators.** The AdSense illegal-content clause names the
  production of false legal documents.

## 5. What to measure

| Metric | Where | What it tells you |
| --- | --- | --- |
| Impressions per tool page | Search Console | Which tools have search demand |
| Referring domains | Search Console | Whether the launch produced links |
| Active View | AdSense | Whether the ad slots are actually rendering |
| Sessions per tool | Analytics | Whether the tool is worth its page |
| Share actions | Analytics | Whether the viral hook is working |
| Inbound link share of total | Search Console | How dependent you are on one source |

The last one matters most. A site whose traffic is 80% from one Reddit post has
a fragile asset, and the fix is the guides, which are the only part of this
project that earns links slowly and permanently.

## 6. Deployment record

What is actually live, so nobody has to rediscover it from the dashboard.

| Thing | Value |
| --- | --- |
| Production URL | <https://devsnap.cc> |
| Host | Cloudflare Pages project `devsnap`, production branch `main` |
| Pages subdomain | `devsnap-4k1.pages.dev` |
| Direct upload | `npx wrangler pages deploy dist --project-name devsnap --branch main` |
| Zone | `devsnap.cc`, plan Free, nameservers `anton`/`edna.ns.cloudflare.com` |
| Apex DNS | `CNAME devsnap.cc → devsnap-4k1.pages.dev`, proxied |
| `www` DNS | `CNAME www.devsnap.cc → devsnap-4k1.pages.dev`, proxied |
| `www` behaviour | Redirect Rule "www to apex": `https://www.devsnap.cc/*` → `https://devsnap.cc/${1}`, 301, path and query preserved |
| Certificates | Google Trust Services WE1, one per hostname, auto-renewed |
| HTTP | "Always Use HTTPS" on, so port 80 is a 301 to 443 |
| HSTS | `max-age=31536000` (no `includeSubDomains`, no preload, so it is reversible) |
| Email | Cloudflare Email Routing: MX `route1..3.mx.cloudflare.net`, SPF, DKIM, no A record on the apex to conflict with the Pages CNAME |

Two details that bit during the setup and are worth remembering:

- Cloudflare only creates the Pages CNAME automatically when the API call that
  adds the custom domain has DNS edit rights. With an OAuth token that has
  `pages:write` but no `zone:write`, the domain sits in `pending` forever and
  the records have to be added by hand.
- `_headers` rules are merged, not replaced. A `Cache-Control` in `/*` plus one
  in `/_astro/*` produces a single response with two values. The fix is a
  `! Cache-Control` detach line in the narrower rule.
